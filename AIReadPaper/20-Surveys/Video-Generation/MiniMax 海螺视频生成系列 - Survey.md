# MiniMax 海螺视频生成系列：从 Video-01 到 H3

## 基本信息

- **覆盖对象**：MiniMax（稀宇科技）海螺（Hailuo）视频模型的三代主线，以及与之直接相关的一篇分词器论文和一篇第三方评测
  - **Hailuo 01 家族**（2024-08 至 2025-03）：Video-01、I2V-01、I2V-01-Live、S2V-01、T2V/I2V-01-Director
  - **Hailuo 02**（2025-06-18）：Noise-aware Compute Redistribution（NCR），原生 1080p
  - **Hailuo 2.3 / 2.3 Fast**（2025-10-28）：在 02 底座上打磨动作、风格化与微表情
  - **VTP**（arXiv 2512.13687，2025-12；华中科技大学 + MiniMax）：面向生成的视觉分词器预训练
  - **MiniMax H3**（2026-07-31 发布，2026-08-03 开放权重）：33B 单流全模态生成模型，音视频联合生成，最高 2K、15 秒
  - **第三方评测**（arXiv 2609.18323，2026-09；NUS / 复旦 / 腾讯）：H3 的物理世界推理能力
- **材料性质**：Hailuo 01 / 02 / 2.3 **没有技术报告或论文**，只有官方发布博客；H3 有官方开源说明与模型卡，但发布博客中承诺的 “H3 Technical Report” **截至 2026-10-25 仍未检索到**。因此本文对 01 / 02 / 2.3 的技术判断大多是基于官方示意图的推断，会逐处标明。
- **命名说明**：“Hailuo 3”“海螺 3”“Hailuo H3”在社区里混用，官方名称是 **MiniMax H3**。H3 起模型名去掉了 “Hailuo” 前缀，“海螺 AI”保留为产品名。

## 一句话结论

海螺三代走的是一条从“专用”到“通用”的路线。**01 代**先把文生 / 图生视频做出来，再用一个个专用分支（Live、主体参考、运镜 Director）补能力；**02 代**用 NCR 在同等参数下把训练和推理效率提高 2.5 倍，再用省下的算力把参数和数据分别扩大 3 倍和 4 倍，主打“同等价格下的质量与物理表现”；**H3** 则主动放弃了 02 的效率架构，改成“语言化上下文表示 + 高压缩 VAE + 33B 单流 Transformer + 自身重生成 2K”，把文生、图生、首尾帧、参考、编辑、音频全部并进同一个模型。贯穿三代的不变量是**对成本的极致追求**：02 靠多分辨率去噪省算力，H3 靠高压缩分词器把序列缩短 4 倍，并把 2K 交给重生成而不是原生训练。

> **我的总体判断：★★★★☆。** H3 是目前少有的“开放权重 + 音视频联合 + 统一参考/编辑”的视频模型，官方的架构披露（VAE 规格、编码器取层、AdaLN 参数占比、2K 重生成方式）相当具体，有很高的参考价值。但它的“开放”有三处明显折扣：**决定质量的 Context-IR 和 2K 重生成没有开源，许可证排除了欧盟、英国、韩国和美国，技术报告迟迟未发**。没有数据配方、训练算力和定量消融，外界很难判断各项设计的真实贡献。

### 1.2 三条贯穿主线

把三代放在一起看，有三条线一直在推进：

1. **任务边界**：01 代是“一个能力一个模型”（T2V、I2V、Live、S2V、Director 各自独立）；02 代收拢成一个更强的通用 T2V / I2V 底座，但参考、编辑仍不在模型内；H3 把文生图、文生视频、文生音频、图 / 视频 / 音频参考与编辑全部写进**同一个预训练目标**，任务关系用自然语言描述。
2. **效率**：02 代在**去噪过程**里省算力（高噪声阶段在低分辨率上算）；H3 在**表示**里省算力（f16t4d24 VAE + 2×2 patchify，等效空间下采样 32 倍），在**系统**里省算力（768p 原生生成，2K 交给重生成），并在训练末期加入原生稀疏注意力。
3. **条件信号**：从短文本 prompt，到带运镜括号指令的 prompt，再到 H3 的 **Context-IR**——一个上千 token 的结构化描述，逐个说明素材之间的关系、保留什么、修改什么、声音是什么。条件越来越“语言化”，这和 MiniMax 在 LLM 侧的积累（M 系列）一脉相承。

## 2. Hailuo 01 家族：从 Video-01 到专用分支

### 2.1 Video-01 与图生视频

MiniMax 在 Hailuo 02 博客中回顾：2024 年 8 月底，他们“非正式地上线了一个早期视频生成模型的 demo 网页”，引起创作者大量关注，随后演变为 Hailuo Video 01 产品。到 2025 年 6 月，Hailuo 01 累计为全球创作者生成了**超过 3.7 亿条视频**。二手资料记录的 Video-01 规格是 720p、25fps、约 6 秒；图生视频（I2V-01）在 2024 年下半年补上。**01 代没有公开任何架构细节**，因此“基于 DiT 的视频扩散模型”只是行业常识层面的推测。

### 2.2 专用分支：Live、主体参考与 Director

01 代后期的特点是**用专用 checkpoint 补能力**：

- **I2V-01-Live**（2024-12）：面向插画和二次元的图生视频，强调表情和动作变化平稳、不崩形。MiniMax 在 2.3 博客中也提到，用户很喜欢 01 代的 “Live” 模型。
- **S2V-01**（2025-01-10）：单图主体参考。官方称它是“首个”在动态视频中、不经微调就能保持人物面部身份的模型，只需一张参考图，姿态、表情、光照仍可由文本控制；官方中文稿称输入和计算成本降到主流方案的 **1% 以下**（对比对象应是逐人物微调的 LoRA 类方案）。官方也坦承局限：S2V-01 的 prompt 遵循有时不如 T2V / I2V，背景偶尔会变形；多主体、物体参考、复杂场景留作后续。
- **T2V-01-Director / I2V-01-Director**（2025 年 2—3 月）：运镜控制。官方强调降低运动随机性、提供预设镜头、提升 prompt 遵循，用户可以用自然语言或 `[Pan left]`、`[Tracking shot]` 这类括号指令指定推、拉、摇、跟等运镜。

**评价**：01 代的产品逻辑是“缺什么能力就训一个专用模型”。这在当时迭代很快，但也正是 H3 博客批判的对象——任务被切成孤岛，既限制创作自由，也限制模型的泛化。

## 3. Hailuo 02：NCR 与效率路线

### 3.1 官方披露的事实

Hailuo 02 于 2025-06-18 发布，官方披露的要点：

- **NCR（Noise-aware Compute Redistribution）**：在可比参数规模下，训练与推理效率提升 **2.5 倍**；
- 节省下来的预算用于扩大模型：总参数量是前代的 **3 倍**，训练数据量是前代的 **4 倍**，数据质量和多样性也有提升；
- 能力上主打**复杂指令遵循**和**极端物理表现**，官方称在体操这类高难度场景中，Hailuo 02 是“目前全球唯一”能达到这种表现的模型（**没有给出定量证据**）；
- 原生 1080p，提供 768p-6s、768p-10s、1080p-6s 三个规格；
- 早期版本在 Artificial Analysis Video Arena 的图生视频榜排名全球第二。

![](assets/MiniMax%20海螺视频生成系列%20-%20Survey/figures/01-hailuo02-ncr.jpeg)

> 图 1：Hailuo 02 博客中的 NCR 示意图。纵轴是噪声水平（下方 T=0 对应纯噪声，上方 T=1 对应干净样本）。左侧在**下采样后的短序列** $l=f\times h\times w$ 上完成高噪声阶段的去噪；到某个噪声水平后，经 “Upsample & Re-noise” 进入右侧的**超长视频 token 序列** $L=F\times H\times W$，继续完成低噪声阶段；两段由同一个 **Shared Model** 完成。图中三条说明：早期步骤可把序列压缩 $\frac{F\times H\times W}{f\times h\times w}$ 倍，既省算力，学习目标也更容易；通过共享参数联合训练两个任务，实现高效的知识共享；精心设计的噪声调度进一步加速训练、便于扩展。
> 来源：MiniMax 官方博客 “MiniMax Hailuo 02, World-Class Quality, Record-Breaking Cost Efficiency”，2025-06-18，https://www.minimax.io/news/minimax-hailuo-02

### 3.2 NCR 的技术解读（个人推断）

官方只有这一张示意图，下面的解读是根据图中信息做的推断：

1. **本质是“同一模型内的多分辨率级联去噪”**。高噪声阶段只决定构图、布局、运动等低频结构，不需要全分辨率，于是在下采样后的 latent 上完成；进入低噪声阶段后，把低分辨率结果上采样并重新加噪到对应的噪声水平，再在全分辨率上细化纹理与细节。思路上与 Pyramidal Flow、Relay Diffusion 一类“分段分辨率 + 重加噪衔接”的工作相近，区别在于两个阶段共享一套参数，作为两个任务联合训练，而不是两个独立的级联模型。
2. **“2.5 倍效率”的来源**。注意力计算量随 token 数平方增长。若空间下采样 2 倍（token 减少约 4 倍），高噪声阶段的注意力开销降到约 1/16，FFN 开销降到约 1/4。只要有相当比例的步数在低分辨率上运行，整体就能节省一半以上的计算。官方没有披露低分辨率阶段的步数比例和下采样倍率。
3. **“Noise-aware” 的含义**：算力按噪声水平重新分配，而不是在所有去噪步上平均分配。这与 [[Flow Matching - 条件概率路径与连续生成]] 中时间步加权、[[Goku - 联合图像视频整流流基础模型]] 等工作的“噪声调度决定学习难度分配”是同一思想在算力维度上的体现。

部分二手资料称 Hailuo 02 使用了 MoE，但**官方博客没有提到 MoE**，本文不采用这一说法。

## 4. Hailuo 2.3：在 02 底座上的能力打磨

Hailuo 2.3 于 2025-10-28 发布，官方明确说它“基于 Hailuo 02 模型”，属于同一代底座上的增量版本：

- **复杂肢体动作**：动作更流畅、自然、精确；在动态运镜下，光线方向、阴影过渡和色调更接近实拍；
- **风格化**：更好地支持动漫、插画、水墨、游戏 CG 等风格，相当于把 01 代 “Live” 专用模型的能力收进通用模型；
- **真人面部表演与微表情**更自然；物体运动指令的响应更好，官方提到电商广告的高质量出片率明显提高；
- **价格与 02 持平**；另推出 **Hailuo 2.3 Fast**，速度更快、价格更低，批量创作成本最多降低 50%；
- 同期把 2025 年夏季上线的 Hailuo Video Agent 升级为 **Media Agent**，自动匹配多模态模型完成“一键成片”，也支持逐步创作。

**评价**：2.3 没有披露任何架构或训练变化，从描述看更像是数据与后训练层面的打磨。值得注意的是两点信号：其一，“把专用模型能力收回通用模型”已经开始（Live → 2.3 的风格化）；其二，Media Agent 说明 MiniMax 已意识到“多模态融合创作是未来”，但此时仍靠**智能体在外部编排多个模型**来实现。H3 则把这种多模态融合从外部编排挪进了模型内部。

## 5. VTP：面向生成的视觉分词器预训练

### 5.1 为什么把它放进这个系列

VTP（Towards Scalable Pre-training of Visual Tokenizers for Generation，arXiv 2512.13687，v2 2026-03-06）由华中科技大学的 Jingfeng Yao、Xinggang Wang 与 MiniMax 的 Yuda Song、Yucong Zhou 完成，代码和权重开源在 MiniMax-AI 组织下，被中文媒体称为“海螺首次开源底层技术”。论文只在图像上做实验（ImageNet、LAION），**并不是 H3 的分词器本身**。但它与 H3 的分词器路线高度相关：

- H3 博客说“H 系列一直在推进分词器技术”，H3 “彻底重做了此前的分词器”，在重建质量和**可学习性（learnability）**上全面提升；
- H3-VisualVAE 的规格是 f16t4d24，VTP 的文生图实验使用的正是 **VTP-f16d24**，空间压缩倍率与通道数都相同；
- H3-AudioVAE 明确写着“受 VA-VAE 启发”，而 VA-VAE 的第一作者正是 VTP 的第一作者 Jingfeng Yao。

因此可以合理推断（**个人判断，未经官方确认**）：VTP 代表了 MiniMax 在“latent 不仅要能重建，还要好学”这一方向上的研究积累，H3 的 VAE 设计受这条线影响。

### 5.2 核心问题：重建越好，生成反而越差

![](assets/MiniMax%20海螺视频生成系列%20-%20Survey/figures/05a-vtp-recon-paradox.png)

> 图 4：只用重建目标训练 ViT 分词器时，随训练 FLOPs 增加，rFID 从 2.07 降到 0.51（重建变好），但下游 DiT 的 gFID 从 55.04 升到 58.56（生成变差）。
> 来源：VTP 论文 Figure 4，第 7 页，https://arxiv.org/abs/2512.13687

作者把这称为 **pre-training scaling problem**：纯重建目标让 latent 偏向低层细节（纹理、边缘、噪点），投入越多算力，latent 越偏离生成模型需要的结构化语义空间。这正是 [[自编码器与变分自编码器家族 - Survey]] 中“VAE 到底在压缩什么”问题在规模化上的直接体现。

### 5.3 方法：重建 + CLIP + 自监督联合训练

![](assets/MiniMax%20海螺视频生成系列%20-%20Survey/figures/04-vtp-overview.png)

> 图 5：VTP 总体框架。以 ViT 作为分词器编码器，同时接三类目标：左侧与文本编码器做图文对比学习（$\mathcal{L}_{clip}$），中间经像素解码器做重建（$\mathcal{L}_{rec}$），右侧按 DINOv2 方式做 EMA 教师的自蒸馏（$\mathcal{L}_{dino}$）与掩码图像建模（$\mathcal{L}_{mim}$）。下方是下游流程：冻结分词器，DiT 在 latent $Z$ 上做 flow matching 训练与采样。
> 来源：VTP 论文 Figure 3，第 5 页，https://arxiv.org/abs/2512.13687

总目标为：

$$\mathcal{L}_{total}=\lambda_{rec}\mathcal{L}_{rec}+\lambda_{ssl}\mathcal{L}_{ssl}+\lambda_{clip}\mathcal{L}_{clip}$$

其中 $\mathcal{L}_{rec}=\mathcal{L}_1+\mathcal{L}_{perceptual}$，$\mathcal{L}_{ssl}=\mathcal{L}_{mim}+\mathcal{L}_{dino}$。几个关键实现细节：

- **全 ViT 自编码器**，瓶颈维度主要用 $d=64$，加 QKNorm 稳定训练；
- **两阶段重建训练**：GAN 损失与 ViT 配合不稳定（梯度范数大），所以预训练阶段只用 L1 + 感知损失，第二阶段冻结分词器、只用 GAN 目标微调像素解码器；
- **异构 batch**：CLIP 需要大 batch（16k），SSL 和重建只需小 batch（4k / 2k），所以从同一个大 batch 中分别子采样；
- **重建权重很小**：$\lambda_{rec}=0.1$，作者发现较小的重建权重反而有利于生成。
- 预训练数据为内部过滤后的 DataComp-1B 子集（2.77 亿样本）；下游统一用 LightningDiT-B 在 ImageNet 上训练 80 epoch，报告 FID-10k。

### 5.4 结论：分词器预训练第一次出现 scaling

![](assets/MiniMax%20海螺视频生成系列%20-%20Survey/figures/05b-vtp-scaling.png)

> 图 6：下游 DiT 训练配置与 FLOPs 固定，只扩大分词器预训练。(a) 数据：AE 从 10 万到 1 亿样本，gFID 只从 58.37 降到 56.71；VTP 从 47.59 降到 27.45。(b) 编码器参数：AE 停在约 57；VTP 从 31.28 降到 26.12。(c) 解码器从 4 层扩到 24 层，VTP 再从 26.12 降到 24.08。
> 来源：VTP 论文 Figure 7，第 9 页，https://arxiv.org/abs/2512.13687

论文的主要结论：

1. **理解能力是生成的关键驱动**：latent 的线性探测精度与下游生成质量强正相关；CLIP 和 SSL 两种范式都能带来相近的提升，三者联合（CLIP+SSL+AE）在同等算力下最好（gFID 27.8、线性探测 74.9%）；
2. **分词器预训练算力扩大 10 倍，下游 DiT 的 FID 改善 65.8%**，而纯重建 AE 在约 1/10 的算力处就已饱和；
3. 最终模型 rFID 0.36、零样本分类 78.2%、线性探测 85.7%，优于 VILA-U、UniTok 等统一分词器；下游 80 epoch 不加引导即可达到 gFID 2.03（快于 VA-VAE、RAE），继续训练最终达到 **gFID 1.11**（ImageNet 256）；
4. 文生图上，加入 CLIP 损失能**明显提升文字渲染能力**。

最后这一点与 H3 主打的“准确的文字与品牌渲染”直接对应。

**局限**：只在图像上验证，没有涉及视频的时间压缩；下游用的是 B 尺寸 DiT 与固定 80 epoch，在大模型、长训练下的结论尚待验证；正文中“同算力下 VTP 收敛更快”与“最终质量更高”的对比口径不完全一致。

## 6. MiniMax H3：任务泛化的全模态生成系统

### 6.1 设计哲学：从“专用”到“通用”

H3 博客对前两代的定位是：“Hailuo 01 从零搭起系统，Hailuo 02 专注于提升架构效率、数据质量和规模等核心组件。”而 H3 的第一原则是**跨任务统一与泛化**。博客明确批评了以往的任务割裂：图像生成被拆成文生图、编辑、主体参考、动作参考、风格参考等专家模型；音频中人声、音效、音乐被分开研究；视频又被拆成文生、图生、首尾帧、主体参考、动作参考、音色参考、视频编辑等。这些孤岛既限制创作自由，也在训练端限制了泛化。

H3 的预训练数据与任务包括：

- **文生图**；
- **文生视频**：所有输出都带联合生成的原生立体声，原生建模多镜头；
- **文生音频**：人声、音效、音乐不做区分，联合建模；
- **泛化的参考与编辑**：图→图、图→视频、音频→音频、音视频→音视频的参考与编辑。

“泛化的参考与编辑”有两个要点：数据**全部来自真实自然数据**，因此有很强的数据可扩展性；参考和编辑关系**用自然语言表达**，而不是限定在固定任务集合里——“语言（或广义的智能结构）是通往泛化的桥梁”。架构和训练上则是“尽早融合多种数据类型与任务，混合比例是关键”。

### 6.2 系统组成：三个模块

![](assets/MiniMax%20海螺视频生成系列%20-%20Survey/figures/06-h3-system-overview.png)

> 图 7：MiniMax H3 系统总览。上下文理解：原始多模态指令经 **H3-Context-IR** 转成结构化上下文表示；基础生成：**H3-Base** 据此生成 768p 音视频；高分辨率重生成：**H3-Regenerate-2K** 同时接收 768p 结果与原始上下文（Context Guidance），重新生成 2K 视频。
> 来源：MiniMax 官方开源说明，2026-08-03，https://www.minimax.io/news/minimax-h3-open-source

**H3-Context-IR（未开源）**：托管的预处理与编排系统，包含指令解析、跨模态关联、时间理解和复杂逻辑推理，把对上下文的理解序列化为 H3-Base 能接受的结构化表示，并在不偏离用户原意的前提下补充缺失的语义细节。官方说它“对最终输出质量至关重要”，强烈建议纳入生成流程。因为它依赖多阶段流程和多个托管模型与服务，所以只提供 API 和提示词写作指南。

开源说明中给出的 Context-IR 输出示例很能说明问题：一个 10 秒文生视频，Context-IR 输出包含逐镜头（`[Shot 1]`、`[Shot 2]`，精确到 `00:04.500` 切镜）的画面描述和单独的 `overall_soundscape` 声音描述，消耗约 8.6K token；参考编辑任务的输出则包含 `subject_definitions`（定义每个主体来自哪张图 / 哪段视频）、`retention_analysis`（逐素材标注 fully_preserved / partially_copy / reference）和 `detailed_description`，单次消耗约 3.9 万 token。

**H3-Base（已开源）**：生成 768p 音视频，详见 6.3。

**H3-Regenerate-2K（未开源）**：见 6.5。

### 6.3 H3-Base 架构

![](assets/MiniMax%20海螺视频生成系列%20-%20Survey/figures/07-h3-base-architecture.png)

> 图 8：H3-Base 架构。① 条件编码：文本进 H3 Encoder（Qwen3-VL-32B，第 50 层特征）；视觉条件同时进 H3 Encoder 与 Visual VAE Encoder（f16t4d24，时间因果，再做 2×2×1 patchify）；音频条件进 Audio VAE Encoder（d=32，立体声，32 kHz → 40 Hz token）。② 打包成一条上下文序列：视觉语义 token、文本 token、视觉参考 latent、音频参考 latent，后接生成目标——带噪音频 latent 与带噪视频 latent。③ H3 Omni Transformer：33B 稠密、单流、音视频联合去噪，模态专属部分只有输入输出头与 AdaLN，主干是 50 层共享 DiT（单流自注意力 + FFN）。④ 解码：视频 latent 经 Visual VAE Decoder 输出 RGB 帧，音频 latent 经 Audio VAE Decoder 输出立体声波形。
> 来源：MiniMax 官方开源说明，2026-08-03，https://www.minimax.io/news/minimax-h3-open-source

逐个组件看：

**H3-Encoder：直接用 Qwen3-VL-32B。** 使用完整的预训练权重，取**第 50 层**隐状态（而不是最后一层）送入 Transformer，并在 tokenizer 中新增 `<d>` 等特殊 token。取中间层是大模型做条件编码器时的常见做法：最后几层偏向下一 token 预测，中间层保留更多通用语义。视觉输入**同时**走 H3-Encoder 和 VAE：前者提供语义理解（“这是谁、在干什么”），后者提供像素级外观（“长什么样”）。这与 [[Qwen3-VL - 长上下文视觉推理与智能体]] 作为多模态理解底座的定位一致。

**H3-VisualVAE：f16t4d24 + 2×2 patchify。** 时间因果的视频自编码器，空间压缩 16 倍、时间压缩 4 倍、24 个 latent 通道；进入 Transformer 前再做 $1\times2\times2$ 的 patchify，等效空间下采样 **32 倍**。编码器训练完成后，**额外训练一个基于 ViT 的解码器**，以降低解码成本并提升重建质量。官方强调对 latent 空间同时优化“重建质量”和“生成模型的易学性”。博客称其高压缩比带来 **4 倍的有效序列长度增益**，是原生 2K 支持的关键技术。（个人推断：4 倍增益意味着前代等效空间下采样约为 16 倍，例如 f8 VAE 配 2×2 patch。）

**H3-AudioVAE：左右声道共享编解码器。** 两个声道各自独立编码、再合并，从而支持立体声输入输出；每个声道把 32 kHz 音频压缩成 **40 Hz** 的 latent 序列，latent 空间“受 VA-VAE 启发”，兼顾重建与可学习性。

**H3-Omni-Transformer：33B 稠密单流。** 刻意采用“相对简单”的 Transformer block 设计以保证可扩展性和泛化：

- 33B 参数中约 **13B 位于 AdaLN 相关分支**。由于 AdaLN 调制输出可以预计算并缓存，纯推理部署时这部分参数不必加载（个人理解：调制只依赖时间步与模态，推理步数固定后可以查表）；
- 注意力层和 FFN 层**没有任何模态专属结构**，模态专属参数只在输入输出层和 AdaLN 分支里；官方称模态专属 AdaLN 以较低的额外成本明显提升了生成质量；
- 使用三维 **MM-RoPE** 编码 $(t,h,w)$ 位置关系；
- 训练最后阶段引入**原生稀疏注意力**，降低长序列成本；开源版只提供全注意力推理，稀疏注意力实现“将在未来更新中单独发布”。

这一设计与 MM-DiT 的“双流、各模态独立权重”相反，走的是 **“共享主干 + 模态专属调制”** 的路线，参数效率更高，也更符合“任务泛化优先于架构技巧”的原则。博客原话是：他们**放弃了 Hailuo 02 的架构**，尽管它曾带来显著的架构优势，因为它会给以任务泛化为中心的模型引入不必要的复杂度——“架构技巧应当让位于模型的定义方式”。

### 6.4 序列长度估算（个人推算）

以 768p、16:9、15 秒为例（官方注明 768p 原生画布上限为 768×1344）：

- 每个 latent 帧 token 数：$\frac{768}{32}\times\frac{1344}{32}=24\times42=1008$；
- 15 秒 × 24 fps = 360 帧，时间因果 4 倍压缩后约 91 个 latent 帧，视频 token 约 **9.2 万**；
- 音频：40 Hz × 15 秒 × 2 声道 = 1,200 token（如果两个声道分别作为 token），远少于视频；
- 文本：Context-IR 输出平均约 4K token（博客称多数素材的理解推理约需 10 万 token，最终蒸馏为平均约 4K token）。

同样时长若直接生成 2K（2560×1440），每帧 $80\times45=3600$ token，总计约 **33 万** token，是 768p 的约 3.6 倍，注意力开销约为 13 倍。这就解释了 H3 为什么在 768p 上训练和生成，把 2K 交给重生成，并需要稀疏注意力。

### 6.5 In-Context Regeneration：用自己做“超分”

H3 的 2K 输出不用传统的超分模块，而是让 H3 基础模型**以 in-context 的方式重新生成**自己的低分辨率结果。官方给出两点理由：一是最大限度复用基础模型已有的生成能力；二是重生成时可以再次读取原始多模态上下文，恢复传统超分只能“猜”的信息，例如小字和精细细节。官方也把它当作“任务泛化”的一个例子。

**个人评价**：这是全系列最有意思的一个设计闭环。Hailuo 02 的 NCR 是在**一个模型内部**做“低分辨率起草 → 上采样重加噪 → 高分辨率精修”；H3 名义上抛弃了 NCR，却在**系统层面**以“768p 生成 → 以 768p 结果和原始上下文为条件重生成 2K”的形式，把“先低后高”的级联思想重新引了回来——只不过不再是专门的架构机制，而是表达成又一个“参考生成”任务，由同一个通用模型完成。

### 6.6 训练与成本

博客和官方中文新闻稿披露的训练与成本信息：

- 引入多模态上下文后，序列长度的方差扩大到原来的 **3 倍**，理解与生成的计算负载明显异构。H3 采用**理解与生成负载分离**的训练架构，分别优化硬件利用率，并兼顾单样本内的异构计算与样本间的负载均衡，端到端训练吞吐提升近 **30%**；
- 借鉴了文本模型中已被验证的方法，包括复杂问题拆解、Reasoning、Scaling Context 和 **Muon 优化器**；
- 发布的 checkpoint 是 **CFG 蒸馏**后的权重，推理时不需要额外的无条件前向；
- 硬件兼容性从设计之初就是重点，官方提到与国产 AI 芯片软硬件协同。
- **未披露**：训练数据规模与来源、训练算力、各阶段配比、去噪步数、各项设计的消融。

**价格**：官方称 2K 下每秒价格不到主流模型的 1/3，768p 价格不到主流模型 720p 的一半；中文新闻稿给出 2K 价格为 0.8 元/秒，并设有峰谷价，谷时为峰时的一半。

3. **技术报告未发**：发布博客说“很快会分享完整的 H3 技术报告”，截至 2026-10-25 未检索到。

## 7. 第三方评测：H3 的物理世界推理

![](assets/MiniMax%20海螺视频生成系列%20-%20Survey/figures/08-h3-reason-eval.png)

> 图 9：评测框架。上方：从世界观测（文本、音频、图像、视频）到模态感知、全模态模型，再到全模态推理与决策；下方四个场景：(a) 多视角空间推理 MSR（左右腕部相机视角同步操作）；(b) 音频消歧推理 ADR（根据“陶瓷碎裂”声判断推落的是哪只杯子）；(c) 视频决策推理 VDR（根据驾驶前缀视频推断应当停车）；(d) 音视频综合推理 AVIR（根据语音规则圈出视频中违规的部分）。
> 来源：Zhao et al., “Can MiniMax-H3 Reason About the Physical World?”, Figure 1，第 2 页，https://arxiv.org/abs/2609.18323

NUS、复旦和腾讯的研究者（含颜水成、吴祖煊）构造了 **517 个样例、4 个领域、29 个子类**的评测，专门让**每个模态只提供部分证据**，必须综合多模态信息才能推断目标事件。由三名专家人工判定生成视频是否满足任务条件（视觉上合理但不满足条件即判为失败）。

| 场景 | 样例数 | 成功率 |
|---|---|---|
| VDR（视频决策推理） | 100 | 56.00% |
| AVIR（音视频综合推理） | 71 | 47.89% |
| MSR（多视角空间推理） | 200 | 43.50% |
| ADR（音频消歧推理） | 146 | 27.40% |
| **总计** | 517 | **41.97%** |

关键发现：

- **超过一半的样例失败**，尽管 H3 支持所需的所有输入模态——“支持多模态输入”不等于“会用多模态证据推理”；
- MSR 内部差异很大：穿线 75.0%、倒水 58.3%，而清洁、铰接物体操作、搬运只有约 33%—35%；
- VDR 对人、动物、交通动态处理较好，但卡通只有 20.00%、拼图只有 16.67%；
- ADR 最难：自然声音较好，机械声、接触声、警报声很难转化为正确的视觉事件；
- 四类失败模式：**证据错配**（找到了合理事件，但把证据关联到错误的对象或动作上，如猫狗混淆）、**事件未完成**（场景里有相关物体，但没有实现输入所暗示的交互，如打字、开罐）、**物理与构型违例**（接触动力学、物体几何、状态转移出错，如滑板、魔方）、**时间状态不一致**。

**评价**：这是目前对 H3 最具体的独立评测，但有三个局限。一是**只测了 H3 一个模型**，没有任何对照，所以 41.97% 无法判断是好是坏；二是作者自己也承认，四个场景的数据、prompt 和目标都不同，**场景之间的差距不能直接解读为视频与音频模态能力的差距**；三是论文没有说明调用方式（是否经过 Context-IR、用 768p 还是 2K）。对 H3 而言，最有价值的信号是：**音频作为“证据”而不是“配乐”时，模型的利用能力很弱**——这与 H3 的音频训练以“联合生成”为主、而非“以音频为因推断视觉”的设定是吻合的（个人判断）。

## 8. 横向对比与演进分析

### 8.1 三代对比

| 维度 | Hailuo 01 家族 | Hailuo 02 / 2.3 | MiniMax H3 |
|---|---|---|---|
| 任务形态 | 每个能力一个专用模型 | 通用 T2V / I2V 底座；参考、编辑在外部（Agent 编排） | 单模型统一文生、首尾帧、多模态参考、编辑 |
| 输出 | 720p，约 6 秒，无声 | 1080p（6 秒）/ 768p（6 或 10 秒），无声 | 768p 原生 / 2K 重生成，4—15 秒，原生立体声 |
| 条件 | 短 prompt；Director 支持运镜指令 | 长 prompt + prompt 优化器 | Context-IR 结构化上下文（数千 token） |
| 核心技术 | 未披露 | NCR：同模型多分辨率去噪 | 高压缩 VAE + 33B 单流 + 模态专属 AdaLN + 2K 重生成 + 稀疏注意力 |
| 效率来源 | — | 去噪过程中重分配算力 | 表示压缩（序列缩短 4 倍）+ 系统级分辨率级联 |
| 开放程度 | 闭源 | 闭源 | 开放 768p 基础权重（有地域限制）；IR / 2K 闭源 |
| 公开技术细节 | 几乎无 | 一张示意图 | 架构规格较详细，无技术报告 |

### 8.2 值得注意的三个演进规律

**规律一：效率机制从“架构”迁移到“表示”与“系统”。** 02 把效率写进了去噪架构，但这种机制与“统一处理任意多模态上下文”冲突：参考视频、音频、文本 token 在低分辨率阶段如何对齐，会让设计变得非常复杂。H3 的选择是把效率前移到 VAE（每个 token 承载更多信息），后移到系统（2K 重生成），中间的 Transformer 保持尽可能朴素。这一取舍与 [[视频生成模型技术谱系与2026现状 - Survey]] 中“分词器压缩率成为视频模型主要效率杠杆”的趋势一致。

**规律二：条件信号的“语言化”。** 从 S2V / Director 的专用接口，到 2.3 的 prompt 优化器，再到 H3 的 Context-IR，MiniMax 越来越倚重“用一个强理解模型，把用户的模糊意图翻译成生成模型能精确执行的长描述”。这与 DALL·E 3 的“重写 caption”思路同源，但 H3 把它推到了多模态关系层面：要描述的不只是目标视频，还有“上下文与目标的关系”和“上下文内部元素之间的关系”。代价是**系统质量的上限被一个闭源的理解模块掌握**，这也是开源版价值被打折扣的根本原因。博客说下一代 H 系列会整合 M 系列的能力，可以预期理解模块会更深地嵌入生成模型。

**规律三：latent 的“可学习性”成为一等公民。** VTP 证明了“重建越好不等于生成越好”，并给出了用语义目标让分词器可扩展的方案；H3 的视觉 VAE 和音频 VAE 都明确把“learnability”与重建质量并列为优化目标。这条线与 REPA、VA-VAE、RAE 等工作汇合，是 2025—2026 年视觉生成最重要的共识之一。

### 8.3 与同期竞品的关系

- **联合音视频生成**：H3 与 Veo 3 系列、Sora 2、Seedance 系列、Kling 3.0 同处“原生带声视频”的第一梯队；它的差异化是**开放权重 + 统一参考/编辑**，劣势是没有公开的定量 benchmark。实时流式音视频的另一条路线可参考 [[OmniForcing - 实时音视频联合流式生成]]。
- **开源视频基座**：相较 [[Wan2.1 - 开源大规模视频生成基础模型]] 这类“完整开源（含训练细节和技术报告）但无音频”的基座，H3 能力更强、更全，但透明度更低，许可证限制也更多。
- **统一单流 Transformer**：H3 的“共享主干 + 模态专属 AdaLN”与 [[Goku - 联合图像视频整流流基础模型]] 的“图像与视频共用一个 full-attention Transformer”属于同一设计哲学，只是 H3 把统一的范围从图像 / 视频扩展到了音频与任意参考。

## 9. 局限与批判性评价

1. **证据层面**：01 / 02 / 2.3 都没有论文或技术报告，NCR 的实际结构、参数规模、训练数据完全未知；“体操场景全球唯一”“效率 2.5 倍”都只是自述。H3 的技术报告承诺至今未兑现，没有数据配方、训练算力、消融和定量 benchmark。
2. **开放性折扣**：开源的是 768p 基础模型，决定质量的 Context-IR 与 2K 重生成闭源；许可证排除了全球最大的几个市场；稀疏注意力未开源，导致本地推理比官方服务更慢。
3. **能力边界**：第三方评测显示，H3 在需要跨模态证据推理时成功率只有约 42%，以音频为证据时只有 27%；官方自己列出的不足包括多模态理解仍有很大提升空间、当前模型规模限制了部分能力、某些场景的视觉细节不足。
4. **评测依赖偏好榜**：系列的“全球第二”“第一”几乎都来自 Artificial Analysis 的 Elo 盲测，缺少物理正确性、长时一致性、身份保持等可复现的定量指标。
5. **版权风险**：海螺 AI 正面临好莱坞片方的版权诉讼（据公开报道），训练数据来源未披露，这对企业部署是实际风险。

## 10. 实践建议与后续问题

### 10.1 想用 H3 做研究或部署

- **本地部署**：按官方 SGLang 示例需要 4 卡（Ulysses 并行度 4）；纯推理时约 13B 的 AdaLN 参数可通过预计算缓存省掉。先用官方 768p 参考输出核对本地部署是否正确，再决定是否接入 Context-IR API。
- **提示词**：一定要读官方的 `VIDEO_PROMPT_WRITING_GUIDE`（base / ref 两份）。Context-IR 的输出格式——逐镜头时间戳、`overall_soundscape`、`subject_definitions` / `retention_analysis`——本身就是最好的 prompt 模板。可以用开源 VLM / LLM 复刻一个简化版 Context-IR。
- **合规**：确认自己所在地区与使用场景是否在许可证允许范围内；商用需标注 “MiniMax H3”；注意“用 H3 输出训练相似模型也算衍生品”的条款。

### 10.2 值得追踪的问题

1. H3 技术报告何时发布，是否会披露数据配方与 VAE 训练细节，H3-VisualVAE 与 VTP 是否确实同源；
2. Regenerate-2K 开源后，“in-context 重生成”与专用超分模型的定量对比（尤其是小字和精细纹理）；
3. 稀疏注意力的具体形式，以及与 MiniMax M3 的 MSA（同为该公司的稀疏注意力方案）是否有关联；
4. 下一代 H 系列整合 M 系列能力后，Context-IR 会不会被吸收进生成模型内部——这决定了开放权重版本与官方服务之间的差距能否缩小；
5. 对 3D / 世界模型方向的启发：“共享主干 + 模态专属 AdaLN + 语言化关系描述”的统一方案，能否迁移到“图像 / 视频 / 3D 资产 / 材质”的统一生成上。
